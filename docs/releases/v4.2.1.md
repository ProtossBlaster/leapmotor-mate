# Mate 4.2.1 — a new installation can be set up again

Installing Mate for the first time did not work. From **4.0.0** the setup page offered a new
installation only one thing: upload an application bundle — a ZIP that has to carry three files,
one of them private application parameters nobody outside the build can produce. The step that asks
for `app.crt` and `app.key`, the two files the instructions name and the only two a user actually
has, had become unreachable. Reported by [@gonzalocav](https://github.com/gonzalocav) in [#328](https://github.com/ProtossBlaster/leapmotor-mate/discussions/328).

Nothing was missing from the build. The certificate pair alone is enough: Mate installs the rest
from the profile packaged inside its own image. Only the page's fork was wrong, and it asked the
wrong question — it looked at whether the installation is managed, which is true for every
installation of the independent client, instead of whether a supplied bundle is needed at all.

## What changes

- **The setup wizard asks for `app.crt` and `app.key` again** on a fresh installation, by file or
  as pasted PEM text, and completes the rest by itself.
- **The bundle upload is still there**, but only where a certificate pair genuinely cannot finish
  the installation — a build with no usable packaged profile.
- **China cloud API research** is recorded in
  [docs/CHINA-API-RESEARCH.md](../CHINA-API-RESEARCH.md), contributed by
  [@kerniger](https://github.com/kerniger) in
  [#326](https://github.com/ProtossBlaster/leapmotor-mate/pull/326): a read-only, verified account
  of the China cloud flow, and why it needs its own adapter rather than a different base URL. It
  documents no change to Mate; Chinese-market accounts remain unsupported.

## Who was affected

Only installations started from scratch on 4.0.0 or later. An installation that already held its
certificate pair — every upgrade from 3.x, and every 4.x install made before the certificate step
disappeared — was never affected and needs nothing.

## Verification

Measured on the released 4.2.0 image with an empty volume, before the change: setup readiness
answered `provisioning_required` and the page showed only the ZIP box, while `POST /api/setup/cert`
with the certificate pair answered `{"ok":true}` and turned readiness to `ready`. After the change,
on the same empty container and in a browser: the certificate step is shown, and its Save button
reaches the endpoint and prints the refusal for unreadable material. The wizard's own
`chooseSetup()` is now run in Node over four readiness answers, and it failed before the fix.

4027 tests in the environment the project pins; the suite on CI is green.

## Update and rollback

Ordinary update: Docker and both Home Assistant add-ons use the same 4.2.1 payload. No credential,
PIN or migration step. Nothing in the database changes.

## Italiano

**Installare Mate da zero non funzionava.** Dalla 4.0.0 la pagina di configurazione offriva a
un'installazione nuova soltanto il caricamento di un pacchetto applicativo: uno ZIP che deve
contenere tre file, uno dei quali è materiale privato che nessuno, fuori dalla build, può produrre.
Il passaggio che chiede `app.crt` e `app.key` — i due file indicati dalle istruzioni, e gli unici
che un utente ha davvero — era diventato irraggiungibile. Segnalato da [@gonzalocav](https://github.com/gonzalocav) nella
[#328](https://github.com/ProtossBlaster/leapmotor-mate/discussions/328).

Alla build non mancava niente: la coppia di certificati basta, perché Mate mette il resto da sé
usando il profilo confezionato nella propria immagine. Sbagliata era solo la scelta della pagina,
che guardava se l'installazione è «gestita» — vero per ogni installazione del client indipendente —
invece di guardare se serva davvero un pacchetto fornito.

Ora la procedura richiede di nuovo `app.crt` e `app.key`, come file o come testo PEM incollato, e
completa da sola. Il caricamento del pacchetto resta, ma solo dove una coppia di certificati non
può davvero bastare. Insieme entra la documentazione della ricerca sul cloud cinese
([docs/CHINA-API-RESEARCH.md](../CHINA-API-RESEARCH.md)), contribuita da
[@kerniger](https://github.com/kerniger) con la [#326](https://github.com/ProtossBlaster/leapmotor-mate/pull/326):
un resoconto in sola lettura di come funziona quel cloud e del perché richieda un adattatore
proprio. Non cambia niente in Mate: gli account del mercato cinese restano non supportati.

**Chi era toccato:** solo chi installava da zero dalla 4.0.0 in avanti. Un'installazione che
possedeva già la propria coppia di certificati — ogni aggiornamento dalla 3.x e ogni installazione
4.x fatta prima che il passaggio sparisse — non è mai stata toccata e non deve fare nulla.

Aggiornamento ordinario, senza credenziali, PIN o migrazione da rifare; il database non cambia.
