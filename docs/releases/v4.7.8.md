# Mate 4.7.8 — a new installation starts cleanly

One correction, found by the Desktop 1.2.0 build before any user met it.

---

## The poller no longer dies on a new installation's first start

On a first start, with an empty data folder, Mate's two processes start together. The web creates
the database schema as it loads, in a write transaction; at the same instant the poller — the
process that records — asks SQLite to switch the new database to its WAL journal. SQLite refuses that
switch **at once** while another connection is writing (it does not wait, because waiting could
deadlock), so the poller stopped with `database is locked` before it recorded anything.

The race was already there; 4.7.7 made it likelier, because both processes now install the
application material behind one lock and leave it at the same instant. The Desktop app's own check,
which starts the real payload in the frozen app on an empty folder, caught it on macOS.

The poller now asks again, for up to 15 seconds — the schema takes milliseconds — and still reports
a lock that never goes away.

## Upgrade impact

Normal update. No schema change, no new setting, nothing to reconfigure. **Existing installations
never met this**: their database is already in WAL, and the switch asks for nothing.

## Verification

- A test holds a write transaction open on a new database, as the web does, and opens the poller's
  database beside it: before, `database is locked` in 0.1 s; now it waits and opens in WAL.
- A database held for good is still reported, after the bound, instead of being waited on for ever.
- Test suite green.

## Italiano

# Mate 4.7.8 — un'installazione nuova parte pulita

Una correzione, trovata dalla build della Desktop 1.2.0 prima che la incontrasse un utente.

---

## Il poller non si ferma più al primo avvio di un'installazione nuova

Al primo avvio, con la cartella dei dati vuota, i due processi di Mate partono insieme. Il web crea
lo schema del database mentre si carica, in una transazione di scrittura; nello stesso istante il
poller — il processo che registra — chiede a SQLite di passare il database nuovo al giornale WAL.
SQLite rifiuta quel passaggio **subito** mentre un'altra connessione sta scrivendo (non aspetta,
perché aspettare potrebbe bloccare tutto), e il poller si fermava con `database is locked` prima di
registrare qualunque cosa.

La corsa c'era già; la 4.7.7 l'ha resa più probabile, perché adesso entrambi i processi installano il
materiale applicativo dietro uno stesso lucchetto e ne escono nello stesso istante. Il controllo della
app Desktop, che avvia il payload vero nell'app congelata su una cartella vuota, l'ha presa su macOS.

Adesso il poller chiede di nuovo, per un massimo di 15 secondi — lo schema richiede millisecondi — e
segnala comunque un lucchetto che non se ne va mai.

## Impatto dell'aggiornamento

Aggiornamento normale. Nessun cambio di schema, nessuna impostazione nuova, niente da riconfigurare.
**Le installazioni esistenti non l'hanno mai incontrato**: il loro database è già in WAL, e il
passaggio non chiede niente.

## Verifica

- Un test tiene aperta una transazione di scrittura su un database nuovo, come fa il web, e apre
  accanto il database del poller: prima, `database is locked` in 0,1 s; adesso aspetta e apre in WAL.
- Un database tenuto per sempre viene comunque segnalato, dopo il limite, invece di essere aspettato
  all'infinito.
- Suite dei test verde.
