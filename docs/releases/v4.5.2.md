# Mate 4.5.2 — the same question, asked once

4.5.1 gave the pages back their old speed. It was not enough: *"non ci siamo ancora lento"*,
*"è assurdo che la pagina veicolo si carichi così lentamente ed è solo un esempio"*.

So every page was profiled with a query counter on a real database, and then measured on the
add-on that had the complaint — aarch64, 90 days of history, roughly four times slower than the
development machine. Seven pages, before and after, median of five requests each:

| page | 4.5.1 | 4.5.2 |
|---|---|---|
| Battery | 3.526 s | **0.121 s** |
| Statistics | 2.679 s | **0.448 s** |
| Trips | 1.696 s | **0.406 s** |
| Settings | 1.613 s | **0.413 s** |
| Monthly report | 0.997 s | **0.307 s** |
| Charges | 0.424 s | **0.256 s** |
| Overview | 0.343 s | **0.195 s** |

Nothing about what Mate shows has changed. Every figure, every label and every button is the one
4.5.1 had; five of the six changes below are the same mistake in different places.

## The mistake

`db_reader.get_setting` opens a **new SQLite connection for every call**. That is cheap enough once.
The code was calling it inside loops.

* **The time zone, 1172 times for one page.** Formatting a stored timestamp for display needs to
  know which zone to show it in, and `_local_dt`/`_local_iso` asked — once per row. Statistics
  issued 1207 queries and 1176 of them were that read; the monthly report, 1284 and 1280. The zone
  is resolved once at the top of each list now and handed down. A held value with a lifetime was
  tried first and was wrong: the poller writes that setting from another process, so a cached answer
  is stale the moment it does, and ten tests said so.

* **Which car, 87 times to draw one card.** `_current_vehicle_id` costs a query, and the battery
  card asked it once per charge examined. The reader already had a way to hold the answer for a
  synchronous stretch — used by the research export so a car switched mid-export cannot change what
  is exported. It is now named `held_vehicle_scope()` and the card uses it.

* **The private key, fourteen times per request.** One call to `/api/vehicle-status` — what the
  Vehicle page fetches after it loads — parsed the account's RSA private key fourteen times: 21 ms
  each on a Mac, and RSA parsing is the slowest thing an aarch64 box does. Both `_apply_session` and
  the saved-session check ask whether the certificate is usable, and both run several times per
  request as reads and commands resume the session. The answer only changes when the files do, so it
  is held per (path, size, mtime) for both of them. A re-issued certificate has a new mtime and is
  read again.

* **Every trip, for every cloud record.** Matching a cloud mileage record to the trip it belongs to
  walked the whole trip history, for each record: over a million `min`/`max` calls per ten renders,
  and `get_trips(3)` — three trips for the Overview — cost 92 ms on the add-on against 1.73 ms on
  3.19.2, where this matching did not exist. Quadratic in the history, so it grew with every drive
  recorded, not with every release, which is what made the releases look guilty. A record can only
  belong to a trip that had already started when the record did, so the trips worth testing are
  found by halving a list sorted by start time, bounded below by the longest trip there is. The
  candidate set is identical — this decides which number a user is shown. 2600 trips and 2600
  records: 0.93 s → 0.11 s.

* **A week of frames, to answer yes or no.** The V2L card asks whether the car has been used as a
  power outlet. It read every position row of the last seven days — 19 731 of them — built a
  dictionary per row and walked them: 57.4 ms of every page, on a card that also refreshes itself
  every ten seconds. A session leaves a mark, so the window is asked about that mark first. On its
  own that made it *worse*, 72.2 ms, because the column had no index and the question was itself a
  scan; with a partial index on it the probe is 0.002 ms and the whole call 1.7 ms.

## Two pages that waited for a long sum

Two figures cannot be made cheap by asking better. The battery health estimate integrates the power
samples of every qualifying charge, and the vampire drain reads ninety days of position rows — about
250 000 — and groups consecutive samples into parks. Both are honest work over data that only grows.

So the pages stop waiting for them. The Battery page's shell arrives and its two sections fetch
themselves; the capacity hint under the Settings capacity field does the same, as the Cloud link card
already did in 4.5.1. The arithmetic is untouched — what changes is that nothing blocks on it. That
is the whole of the 3.526 s → 0.121 s on Battery, and 0.927 s of the Settings figure.

## A dot that kept dialling

Deciding the colour of the MQTT status dot opens a real TCP connection to the broker: **1.011 s** on
the add-on. The Settings card asked for it on load and every 30 seconds — so while that page was
open, whether or not anyone had expanded the MQTT card, the box spent a second dialling a broker
every half minute. The same macro drives the ABRP dot, which reaches the ABRP service. The first
reading still happens, because the collapsed summary is meant to show the colour; the repeat now
runs only while the card is open.

## The database is not the problem

The obvious question was whether SQLite had run out of room and a real server with real indexes
would be faster. It would not have helped: the cost was never in *answering*, it was in *asking*.
One of these fixes added an index and took a 12.7 ms scan to 0.002 ms — on the same SQLite. The
timezone fix removed 1172 reads from one page; over a network connection to a database server those
same 1172 reads would each have become a round trip.

## What this does not fix

Three things are known, measured, and deliberately left for their own piece of work:

* **The map page** serialises the whole GPS track into the HTML — 296 KB — and draws it in
  JavaScript. The queries behind it cost 70 ms; the page weight is the rest. Moving the track to its
  own fetch means rewriting the drawing code, including how it bridges gaps in the signal.
* **`/api/battery-vampire`, 2.322 s.** It walks 250 000 rows in Python at about 2 µs each. Reducing
  that means asking SQL for only the rows where something changes, which is a redesign of how a stop
  is recognised — and that logic carries two open reports of its own (#41, #63).
* **`/api/battery-health`, 1.073 s.** One position read per charge, about 180 queries. Reading them
  in one go and splitting in Python is straightforward but touches two functions and their tests.

None of the three blocks a page any more: both battery sections load after their page, and the map
is the fastest of the slow ones at 0.478 s.

## Verification

- The whole suite: **4327 passed, 1 skipped**. Every new test was seen fail first.
- Measured on the add-on that reported the problem, by its owner, not on the development machine.
- The MQTT change checked on a running container: eighty seconds with every card closed, no calls.
- All the API routes swept against a copy of a real database, before and after.

## Update and rollback

Nothing to do. One index is added to the `positions` table on first start — a partial index on the
V2L marker, created after the column exists. It is created if missing and nothing else about the
schema, the settings or the stored data changes, so rolling back to 4.5.1 costs only the speed.

## Italiano

# Mate 4.5.2 — la stessa domanda, chiesta una volta

La 4.5.1 ha restituito alle pagine la velocità di prima. Non è bastato: *«non ci siamo ancora
lento»*, *«è assurdo che la pagina veicolo si carichi così lentamente ed è solo un esempio»*.

Così ogni pagina è stata passata al contatore di query su un database vero, e poi misurata
sull'add-on da cui veniva la segnalazione — aarch64, 90 giorni di storia, circa quattro volte più
lento della macchina di sviluppo. Sette pagine, prima e dopo, mediana di cinque richieste:

| pagina | 4.5.1 | 4.5.2 |
|---|---|---|
| batteria | 3,526 s | **0,121 s** |
| statistiche | 2,679 s | **0,448 s** |
| viaggi | 1,696 s | **0,406 s** |
| impostazioni | 1,613 s | **0,413 s** |
| report mensile | 0,997 s | **0,307 s** |
| ricariche | 0,424 s | **0,256 s** |
| panoramica | 0,343 s | **0,195 s** |

Di quello che Mate mostra non è cambiato niente. Ogni cifra, ogni etichetta e ogni bottone sono
quelli della 4.5.1; cinque delle sei correzioni qui sotto sono lo stesso errore in posti diversi.

## L'errore

`db_reader.get_setting` apre **una connessione SQLite nuova a ogni chiamata**. Una volta sola costa
poco. Il codice la chiamava dentro i cicli.

* **Il fuso orario, 1172 volte per una pagina.** Per scrivere una data salvata bisogna sapere in
  quale fuso mostrarla, e `_local_dt`/`_local_iso` lo chiedevano — una volta per riga. Le statistiche
  facevano 1207 query e 1176 erano quella lettura; il report mensile 1284 e 1280. Adesso il fuso si
  risolve una volta in testa a ogni elenco e si passa giù. Prima era stato provato un valore tenuto
  in memoria con una scadenza, ed era sbagliato: quell'impostazione la scrive il poller da un altro
  processo, quindi una risposta tenuta è vecchia dal momento in cui lo fa — dieci test l'hanno detto.

* **Quale auto, 87 volte per disegnare un riquadro.** `_current_vehicle_id` costa una query, e il
  riquadro della batteria la chiedeva una volta per ricarica esaminata. Il lettore aveva già un modo
  per tenere la risposta per un tratto sincrono — lo usa l'esportazione per la ricerca, perché un
  cambio d'auto a metà non cambi cosa si sta esportando. Ora si chiama `held_vehicle_scope()` e il
  riquadro lo usa.

* **La chiave privata, quattordici volte per richiesta.** Una chiamata a `/api/vehicle-status` —
  quella che la pagina del veicolo fa dopo essersi aperta — leggeva e interpretava la chiave RSA
  dell'account quattordici volte: 21 ms a botta su un Mac, e interpretare una RSA è la cosa più
  lenta che sa fare una macchina aarch64. Sia `_apply_session` sia il controllo della sessione
  salvata chiedono se il certificato è usabile, e girano più volte per richiesta mentre letture e
  comandi riprendono la sessione. La risposta cambia solo se cambiano i file, quindi si tiene per
  (percorso, dimensione, data di modifica) di entrambi. Un certificato riemesso ha una data nuova e
  viene riletto.

* **Tutti i viaggi, per ogni record del cloud.** Per collegare un record di chilometraggio del cloud
  al viaggio a cui appartiene si percorreva tutta la storia dei viaggi, per ciascun record: oltre un
  milione di `min`/`max` ogni dieci aperture, e `get_trips(3)` — tre viaggi per la panoramica —
  costava 92 ms sull'add-on contro 1,73 ms sulla 3.19.2, dove questo collegamento non c'era. È
  quadratico nella storia, quindi peggiorava a ogni viaggio registrato e non a ogni release: è
  questo che faceva sembrare colpevoli le release. Un record può appartenere solo a un viaggio già
  iniziato quando il record è stato scritto, quindi i viaggi da provare si trovano dimezzando un
  elenco ordinato per orario di partenza, con un limite in basso pari al viaggio più lungo che
  esiste. L'insieme dei candidati è identico — qui si decide quale numero vede una persona. Con 2600
  viaggi e 2600 record: 0,93 s → 0,11 s.

* **Una settimana di frame, per rispondere sì o no.** Il riquadro V2L chiede se l'auto è stata usata
  come presa di corrente. Leggeva tutte le righe di posizione degli ultimi sette giorni — 19.731 —
  costruiva un dizionario per riga e le percorreva: 57,4 ms su ogni pagina, su un riquadro che si
  aggiorna anche ogni dieci secondi. Una sessione lascia un segno, quindi alla finestra si chiede
  prima di quel segno. Da solo questo peggiorava le cose, 72,2 ms, perché la colonna non aveva
  indice e la domanda era essa stessa una scansione; con un indice parziale la verifica è 0,002 ms e
  l'intera chiamata 1,7 ms.

## Due pagine che aspettavano un conto lungo

Due cifre non si fanno costare meno chiedendo meglio. La stima di salute della batteria integra i
campioni di potenza di ogni ricarica valida, e il consumo da fermo legge novanta giorni di righe di
posizione — circa 250.000 — e raggruppa i campioni consecutivi in soste. Sono conti onesti su dati
che solo crescono.

Quindi le pagine non li aspettano più. Lo scheletro della pagina batteria arriva e le sue due sezioni
si scaricano da sole; l'indicazione della capacità sotto il campo nelle impostazioni fa lo stesso,
come già il riquadro «Collegamento al cloud» nella 4.5.1. L'aritmetica non è stata toccata — cambia
che nessuno ci aspetta sopra. È tutto lì il 3,526 s → 0,121 s della batteria, e 0,927 s di quello
delle impostazioni.

## Un pallino che continuava a chiamare

Decidere il colore del pallino di stato MQTT apre una connessione TCP vera al broker: **1,011 s**
sull'add-on. Il riquadro delle impostazioni lo chiedeva all'apertura e ogni 30 secondi — quindi
finché quella pagina era aperta, che qualcuno avesse espanso il riquadro MQTT o no, la macchina
spendeva un secondo a chiamare un broker ogni mezzo minuto. Lo stesso pezzo di codice regge il
pallino di ABRP, che va al servizio ABRP. La prima lettura resta, perché il riassunto chiuso il
colore lo deve mostrare; la ripetizione ora gira solo mentre il riquadro è aperto.

## Il database non è il problema

La domanda ovvia era se SQLite fosse arrivato al limite e un server vero con indici veri andasse più
veloce. Non avrebbe aiutato: il costo non è mai stato nel *rispondere*, era nel *chiedere*. Una di
queste correzioni ha aggiunto un indice e ha portato una scansione da 12,7 ms a 0,002 ms — sullo
stesso SQLite. La correzione del fuso orario ha tolto 1172 letture da una pagina; su una connessione
di rete verso un server di database quelle stesse 1172 letture sarebbero diventate 1172 andate e
ritorno.

## Cosa questo non risolve

Tre cose sono note, misurate e lasciate di proposito a un lavoro loro:

* **La pagina mappa** scrive tutta la traccia GPS dentro l'HTML — 296 KB — e la disegna in
  JavaScript. Le query dietro costano 70 ms; il resto è il peso della pagina. Spostare la traccia in
  una richiesta sua vuol dire riscrivere il codice che la disegna, compreso come colma i buchi di
  segnale.
* **`/api/battery-vampire`, 2,322 s.** Percorre 250.000 righe in Python a circa 2 µs l'una. Ridurle
  vuol dire chiedere a SQL solo le righe in cui cambia qualcosa, e quello è un ridisegno di come si
  riconosce una sosta — logica che porta con sé due segnalazioni aperte (#41, #63).
* **`/api/battery-health`, 1,073 s.** Una lettura di posizioni per ricarica, circa 180 query.
  Leggerle in un colpo e dividerle in Python è lineare, ma tocca due funzioni e i loro test.

Nessuna delle tre blocca più una pagina: le due sezioni della batteria si caricano dopo la loro
pagina, e la mappa è la più veloce fra le lente, 0,478 s.

## Verifica

- Tutta la suite: **4327 passati, 1 saltato**. Ogni test nuovo è stato visto rosso prima.
- Misurato sull'add-on che ha segnalato il problema, dal suo proprietario, non sulla macchina di
  sviluppo.
- La modifica MQTT provata su un container in funzione: ottanta secondi con tutti i riquadri chiusi,
  nessuna chiamata.
- Tutte le rotte API passate su una copia di un database vero, prima e dopo.

## Aggiornamento e ritorno indietro

Niente da fare. Al primo avvio viene aggiunto un indice alla tabella `positions` — un indice parziale
sul segno del V2L, creato dopo che la colonna esiste. Viene creato se manca e del resto non cambia
nulla né nello schema, né nelle impostazioni, né nei dati salvati, quindi tornare alla 4.5.1 costa
solo la velocità.
