# Mate 4.25.0 — a security release

A web page on another site could drive a Mate that has no password, the doors included. A Mate with no
password now answers only on the names a home network uses. The add-on's port 4000, the Home Assistant
token and the web libraries are fixed too. **Update.** If you open Mate through a public name without a
password, read *Upgrade impact* first.

---

## What changes

### A page on another site cannot drive Mate

Mate already refused a form sent from another site. But a page can make a name of its own point at your
Mate's address (DNS rebinding): to Mate the page then looks like Mate itself. On 4.24.0, with no password,
which is how Mate is installed, such a page changed a setting and read Mate's data back. Every command of the
API sat behind the same check, and unlock uses the PIN Mate stores.

| Mate with no password, opened as | Before | After |
|---|---|---|
| an IP address, `localhost`, a name without dots, `.local`, `.lan`, `.home`, `.home.arpa`, `.internal` | answers | answers |
| any other name (a public name, a `*.ts.net` name, `nip.io`) | answers | refused, unless named in `MATE_ALLOWED_HOSTS` |

- With a password set, nothing changes: a page on another site has no session.
- `MATE_ALLOWED_HOSTS` takes host names, comma-separated, port optional. The hosts already in
  `MATE_TRUSTED_ORIGINS` count as named. See `.env.example`.
- `/healthz` answers on any name, as before.

### The add-on's port 4000 has the same guards as a standalone Mate

The add-on switched every guard off, because Home Assistant's panel (ingress) already authenticates. The
switch held for requests on port 4000 too, which is closed until you open it.

| Add-on | Before | After |
|---|---|---|
| The Home Assistant panel | unchanged | unchanged |
| Port 4000, a form from another site | accepted | refused |
| Port 4000, inside a frame on another site | allowed | refused |
| Port 4000, a public name | answers | refused: use the panel or the machine's address |

The panel is recognised by the address Home Assistant's ingress connects from, `172.30.32.2`, which the
Home Assistant developer documentation tells an add-on to expect.

### The Home Assistant token goes only over a verified connection

Mate sent the Home Assistant token without checking the server's certificate, for every address. The
token opens the whole house. Now:

| Home Assistant URL | Certificate |
|---|---|
| a private address, a Tailscale `100.x` address, a home-network name | not checked, as before (self-signed is fine) |
| a public name, a Nabu Casa URL | checked |

### The web libraries are moved off versions with published advisories

| Library | 4.24.0 | 4.25.0 | Advisories on the old version |
|---|---|---|---|
| FastAPI / Starlette | 0.115.0 / 0.38.6 | 0.162.2 / 1.10.0 | 8 |
| python-multipart | 0.0.9 | 0.0.33 | 7 |
| Pillow | 12.3.0 | 13.0.0 | about 45 |
| Jinja2 | 3.1.4 | 3.1.6 | 3 |
| cryptography | 48.0.1 | 50.0.2 | 3 |

The one that mattered most: the login page read a whole form before checking the password. On 4.24.0
one 400 MB field took the web from 111 to 657 MB of memory; on 4.25.0 the request is cut off and the
memory does not grow. Pillow reads only the car picture downloaded from the Leapmotor cloud; the
Jinja2 and cryptography advisories touch parts Mate does not use.

### The desktop app on a Mac starts Mate again

4.24.0 made the lock the web and the poller share hold on a Docker Desktop folder by taking two locks. On a
Mac itself, where the desktop app runs, those two locks are one: the process waited for its own lock, and
neither the web nor the poller got past their start. Measured with the desktop app's own test on a Mac: the
web never opened its port with 4.24.0's lock, and answered in 1.9 s with this one. On a Mac it now takes one
lock, as before 4.24.0; Docker, Linux and Windows are unchanged.

### Smaller ones

- **Changing the password signs everyone else out.** A session stayed valid for its 30 days whatever
  happened to the password.
- **The address of the car is text, never markup**, and values written into a page's scripts are
  escaped.

## Upgrade impact

- **No password, opened through a public name** (a DuckDNS name, a Tailscale `*.ts.net` name, a reverse
  proxy or tunnel that passes the public name on — whether yours does depends on its settings): Mate answers *Mate answers on this name only
  with a password*. Open Mate by its address on your network and set a password in *Settings → Access*,
  or name the host in `MATE_ALLOWED_HOSTS` and restart.
- **With a password:** sign in once more after the update.
- **Home Assistant on a public name with a self-signed certificate:** the connection stops. Use its
  local address in *Settings*, or give it a valid certificate.
- **Desktop app:** Mate 4.25.0 needs [MateDesktop 1.2.3](https://github.com/ProtossBlaster/MateDesktop/releases), which carries the new libraries. Desktop 1.2.2 does not take this update and shows *A newer version of the app is required — download it*.
- **Add-on:** nothing to do for the panel. Port 4000, if you opened it, answers on the machine's address
  or `homeassistant.local`, not on a public name, and cannot be shown inside another page.
- No schema change.

## Verification

- The full suite: 6,059 passed, 6 skipped. Each new test of a fix fails on 4.24.0 and passes on 4.25.0;
  the new tests of what must not change (the LAN, the panel, a self-signed Home Assistant at home) pass on both.
- On an image built from this release, in throwaway containers:
  - Standalone, no password: a write and a read with `evil.com` as name and origin were refused (403),
    and the same for `rebind.attacker.net`, `192.168.1.50.nip.io` and a `*.ts.net` name. The same write
    with an IP address went through (204), and so did a read on `nas.local` and on `mate`.
  - With `MATE_ALLOWED_HOSTS` naming the `*.ts.net` host, the write on that name went through and
    `evil.com` stayed refused.
  - With a password, a public name got the login (401).
  - Add-on, from another machine: a form from another site refused, a public name refused, the IP
    address answered, every response not to be framed. From `172.30.32.2`, as ingress connects: a write
    with Home Assistant's origin went through and no anti-frame header was sent, as on 4.24.0.
  - 400 MB on `/login`: the request cut off, memory from 114 to 112 MB, the web still answering.
  - Every page in demo mode: 19 of 19 answered 200, no error in the logs.

## Italiano

# Mate 4.25.0 — un rilascio di sicurezza

Una pagina web di un altro sito poteva comandare un Mate senza password, porte comprese. Ora un Mate senza
password risponde solo ai nomi che usa una rete di casa. Corrette anche la porta 4000 dell'add-on, il token
di Home Assistant e le librerie web. **Aggiorna.** Se apri Mate con un nome pubblico senza password, leggi
prima *Impatto dell'aggiornamento*.

---

## Cosa cambia

### Una pagina di un altro sito non può comandare Mate

Mate rifiutava già un form spedito da un altro sito. Ma una pagina può far puntare un nome suo
all'indirizzo del tuo Mate (DNS rebinding): per Mate quella pagina sembra Mate stesso. Sulla 4.24.0, senza
password, che è come Mate si installa, una pagina così ha cambiato un'impostazione e ha riletto i dati di
Mate. Ogni comando dell'API stava dietro lo stesso controllo, e lo sblocco usa il PIN che Mate tiene salvato.

| Mate senza password, aperto come | Prima | Dopo |
|---|---|---|
| un indirizzo IP, `localhost`, un nome senza punti, `.local`, `.lan`, `.home`, `.home.arpa`, `.internal` | risponde | risponde |
| qualunque altro nome (un nome pubblico, un nome `*.ts.net`, `nip.io`) | risponde | rifiutato, se non è in `MATE_ALLOWED_HOSTS` |

- Con una password non cambia niente: una pagina di un altro sito non ha la sessione.
- `MATE_ALLOWED_HOSTS` prende nomi di host separati da virgola, porta facoltativa. Gli host già in
  `MATE_TRUSTED_ORIGINS` contano come nominati. Vedi `.env.example`.
- `/healthz` risponde su qualunque nome, come prima.

### La porta 4000 dell'add-on ha le stesse protezioni di un Mate standalone

L'add-on spegneva tutte le protezioni, perché il pannello di Home Assistant (ingress) autentica già.
L'interruttore valeva anche per le richieste sulla porta 4000, che è chiusa finché non la apri tu.

| Add-on | Prima | Dopo |
|---|---|---|
| Il pannello di Home Assistant | invariato | invariato |
| Porta 4000, un form da un altro sito | accettato | rifiutato |
| Porta 4000, dentro un frame di un altro sito | permesso | rifiutato |
| Porta 4000, un nome pubblico | risponde | rifiutato: usa il pannello o l'indirizzo della macchina |

Il pannello si riconosce dall'indirizzo da cui si collega l'ingress di Home Assistant, `172.30.32.2`, che la
documentazione per sviluppatori di Home Assistant dice a un add-on di aspettarsi.

### Il token di Home Assistant passa solo su una connessione verificata

Mate mandava il token di Home Assistant senza controllare il certificato del server, per ogni indirizzo.
Quel token apre tutta la casa. Ora:

| URL di Home Assistant | Certificato |
|---|---|
| un indirizzo privato, un indirizzo Tailscale `100.x`, un nome della rete di casa | non controllato, come prima (va bene autofirmato) |
| un nome pubblico, un URL Nabu Casa | controllato |

### Le librerie web lasciano le versioni con vulnerabilità pubblicate

| Libreria | 4.24.0 | 4.25.0 | Avvisi sulla versione vecchia |
|---|---|---|---|
| FastAPI / Starlette | 0.115.0 / 0.38.6 | 0.162.2 / 1.10.0 | 8 |
| python-multipart | 0.0.9 | 0.0.33 | 7 |
| Pillow | 12.3.0 | 13.0.0 | circa 45 |
| Jinja2 | 3.1.4 | 3.1.6 | 3 |
| cryptography | 48.0.1 | 50.0.2 | 3 |

La più importante: la pagina di accesso leggeva tutto il form prima di controllare la password. Sulla
4.24.0 un solo campo da 400 MB ha portato il web da 111 a 657 MB di memoria; sulla 4.25.0 la richiesta
viene interrotta e la memoria non cresce. Pillow legge solo l'immagine dell'auto scaricata dal cloud
Leapmotor; gli avvisi di Jinja2 e cryptography riguardano parti che Mate non usa.

### L'app desktop su Mac avvia di nuovo Mate

La 4.24.0 ha fatto reggere su una cartella di Docker Desktop il lucchetto che web e poller condividono,
prendendone due. Sul Mac stesso, dove gira l'app desktop, quei due lucchetti sono uno: il processo aspettava
il proprio lucchetto, e né il web né il poller superavano l'avvio. Misurato col test dell'app desktop su un
Mac: con il lucchetto della 4.24.0 il web non ha mai aperto la porta, con questo ha risposto in 1,9 s. Sul Mac
ora ne prende uno, come prima della 4.24.0; Docker, Linux e Windows non cambiano.

### Le più piccole

- **Cambiare la password fa uscire tutti gli altri.** Una sessione restava valida i suoi 30 giorni,
  qualunque cosa succedesse alla password.
- **L'indirizzo dell'auto è testo, mai codice della pagina**, e i valori scritti negli script di una
  pagina sono protetti.

## Impatto dell'aggiornamento

- **Senza password, aperto con un nome pubblico** (un nome DuckDNS, un nome Tailscale `*.ts.net`, un
  reverse proxy o un tunnel che passa il nome pubblico — se il tuo lo fa dipende dalle sue impostazioni): Mate risponde *Mate answers on this name
  only with a password*. Apri Mate con il suo indirizzo di rete e imposta una password in
  *Impostazioni → Accesso*, oppure scrivi il nome in `MATE_ALLOWED_HOSTS` e riavvia.
- **Con una password:** dopo l'aggiornamento rifai l'accesso una volta.
- **Home Assistant su un nome pubblico con certificato autofirmato:** la connessione si ferma. Usa il suo
  indirizzo locale in *Impostazioni*, oppure dagli un certificato valido.
- **App desktop:** Mate 4.25.0 ha bisogno di [MateDesktop 1.2.3](https://github.com/ProtossBlaster/MateDesktop/releases), che porta le librerie nuove. Desktop 1.2.2 non prende questo aggiornamento e mostra *Serve una versione più recente dell'app — scaricala*.
- **Add-on:** niente da fare per il pannello. La porta 4000, se l'hai aperta, risponde sull'indirizzo
  della macchina o su `homeassistant.local`, non su un nome pubblico, e non si può mostrare dentro
  un'altra pagina.
- Nessun cambio di schema.

## Verifica

- La suite completa: 6.059 passati, 6 saltati. Ogni test nuovo di una correzione fallisce sulla 4.24.0 e passa
  sulla 4.25.0; i test nuovi di ciò che non deve cambiare (la rete di casa, il pannello, un Home Assistant
  autofirmato in casa) passano su entrambe.
- Su un'immagine costruita da questo rilascio, in container usa e getta:
  - Standalone, senza password: una scrittura e una lettura con `evil.com` come nome e origine
    rifiutate (403), e lo stesso per `rebind.attacker.net`, `192.168.1.50.nip.io` e un nome `*.ts.net`.
    La stessa scrittura con un indirizzo IP è passata (204), e così una lettura su `nas.local` e su `mate`.
  - Con `MATE_ALLOWED_HOSTS` che nomina l'host `*.ts.net`, la scrittura su quel nome è passata ed
    `evil.com` è rimasto rifiutato.
  - Con una password, un nome pubblico ha ricevuto il login (401).
  - Add-on, da un'altra macchina: form da un altro sito rifiutato, nome pubblico rifiutato, l'indirizzo IP
    ha risposto, ogni risposta non incorniciabile. Da `172.30.32.2`, come si collega l'ingress: una
    scrittura con l'origine di Home Assistant è passata e nessuna intestazione anti-frame, come sulla 4.24.0.
  - 400 MB su `/login`: richiesta interrotta, memoria da 114 a 112 MB, il web risponde ancora.
  - Ogni pagina in modalità demo: 19 su 19 hanno risposto 200, nessun errore nei log.
