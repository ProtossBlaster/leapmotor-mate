# Mate 4.5.3 — one connection, not one per read

4.5.2 stopped Mate asking the same question once per row. This release stops it paying for the
question at all.

Measured on the add-on that reported the slowness — aarch64, 90 days of history, 284 505 position
rows — by its owner, median of five requests each:

| page | 4.5.2 | 4.5.3 |
|---|---|---|
| Overview | 0.213 s | **0.048 s** |
| Battery | 0.129 | **0.012** |
| Charges | 0.278 | **0.035** |
| Statistics | 0.489 | **0.163** |
| Monthly report | 0.323 | **0.156** |
| Trips | 0.422 | **0.231** |
| Map | 0.491 | **0.362** |
| Settings | 0.448 | **0.311** |
| `/api/battery-health` | 1.150 | **0.114** |
| `/api/battery-vampire` | 2.427 | **0.929** |
| `/api/vehicle-status` | 0.551 | **0.447** |

Nothing about what Mate shows has changed.

## The cost was in asking

`db_reader` opened a **brand-new SQLite connection on every read**. `get_setting` costs about 124 µs
not because the query is hard but because the connection is new and its page cache is cold — and 119
queries in that module go through it, with one page render calling dozens of readers.

There is now **one read connection per thread**. It is let go when the database path moves, or when
the file under that path is replaced — the key includes the file's identity, so a restore from backup
is picked up rather than silently ignored.

Sharing it holds nothing back. The connection is read-only and SQLite gives each statement its own
read transaction, so a commit from the poller — a different process — is visible on the very next
read, and a test proves exactly that. This is the difference from the approach tried and rejected in
4.5.2: a cached *value* goes stale the moment someone else writes, a shared connection does not.

## Proving a negative

`/api/battery-health` was 1.150 s. Profiled against a real database, the whole estimate came to
214 ms and **184.57 ms of it was one query, called eleven times**: the probe asking whether anyone
sat in the car with the heater or cooler running while it charged — a charge like that has its
energy/SoC ratio distorted and is left out of the figure.

It looks cheap (`SELECT 1 … LIMIT 1`) and that is exactly why it was expensive: with no index on
those two columns, finding **no** match means reading every frame in the charge window. Timed on its
own over all 33 charges of that database: **618 ms**, plan `SCAN positions`, and not one of those
charges had the cabin in use. A partial index holding only the frames where it was — 2081 rows out of
374 511 — turns the plan into a search and those 33 probes into 0.10 ms.

## Three more clocks

4.5.2 hoisted the time zone out of five loops. A profile of what was left found three more, all in
closures rather than in the visible loop:

* the standby-drain card read the setting **twice per park closed** — 1608 reads for one card;
* the polling strip formats 288 windows with two ends each — **578 reads**, and the zone was already
  resolved at the top of that same function;
* the battery chart read it once per charge dated.

## The drain card

`/api/battery-vampire` reads ninety days of position rows and groups consecutive samples into parks.
There is no index that helps: it is honest work over data that only grows. What it no longer does is
build a `sqlite3.Row` for each of 284 505 frames. On the lab, same 47 windows and 177 rejections
every time:

    4.5.0                          494.3 ms
    + the time zone hoisted        301.5 ms
    + plain tuples off the cursor  209.2 ms

On the add-on, that last step is **1.316 s → 0.929 s**.

The reply is not merely equal but identical — the whole thing dumped to JSON from the old reader and
the new one diffs to zero lines.

## Two defects this found

Neither had ever reached anyone: both needed the shared connection to become reachable, and both are
fixed in the same release that made them reachable.

* Refuels live in a table created on first use, and thirteen read paths asked for it to be created
  on a **read-only** connection, most of them wrapping that call and their own query in one
  `except`. On a fresh connection it never failed, because `CREATE TABLE IF NOT EXISTS` is a no-op
  against a schema that already holds the table. On a connection opened before the first refuel it
  does try to write, and from then on the query behind it would have been skipped — a total silently
  missing every litre of petrol ever entered.
* The update check calls GitHub with a six-second timeout and then records that it ran, resolving the
  database path when the thread finally gets there. It now writes to the database it was scheduled
  for. This matters beyond tests: that write opens the path with sqlite3's default flags, which
  **create** an empty database when the file is not there, so a job pointed at the wrong path could
  leave behind something that looks like a fresh install.

## What this does not fix, and why

Each of these was measured before being left alone:

* **Settings, 0.311 s.** Every database read behind that page, added up, costs **0.17 ms**. The rest
  is rendering 149 KB of HTML. There is nothing to fix in the reader; making it faster means the
  cards fetching their own bodies, one product decision at a time, as the Cloud link card already
  does.
* **The map, 0.362 s.** The query is 24.5 ms and already uses its index. It reads 47 936 points to
  draw 11 791 — every trip ever recorded, which is what the page is for. Reading them as tuples
  would give about 13%, at the cost of rewriting the row access of two functions shared by the global
  map and the month map. The lever that matters is the existing "how many trips to show" setting,
  which is set to *all*.
* **`/api/vehicle-status`, 0.447 s.** It asks the car, through Leapmotor's cloud. Timed on its own it
  is 517 ms and **five queries**: what is left is the cloud answering, not Mate. The 213 database
  connections per call that used to be in there are gone.

## Verification

- The whole suite: **4347 passed, 1 skipped**, one pre-existing warning. Every new test was seen fail
  first, and the two defects above were each re-broken to check the test catches them.
- The before/after above was run by the add-on's owner on his own hardware, not on a development
  machine, and the script refuses to report an "after" unless the container actually restarted.
- The drain card's reply was diffed, not just timed.

## Update and rollback

Nothing to do. One partial index is added to the `positions` table at first start, created after the
columns it indexes exist. Nothing else about the schema, the settings or the stored data changes, so
rolling back to 4.5.2 costs only the speed.

## Italiano

# Mate 4.5.3 — una connessione, non una per lettura

La 4.5.2 ha smesso di chiedere la stessa cosa una volta per riga. Questa smette di pagare la domanda.

Misurato sull'add-on da cui veniva la segnalazione — aarch64, 90 giorni di storia, 284.505 righe di
posizione — dal suo proprietario, mediana di cinque richieste:

| pagina | 4.5.2 | 4.5.3 |
|---|---|---|
| panoramica | 0,213 s | **0,048 s** |
| batteria | 0,129 | **0,012** |
| ricariche | 0,278 | **0,035** |
| statistiche | 0,489 | **0,163** |
| report mensile | 0,323 | **0,156** |
| viaggi | 0,422 | **0,231** |
| mappa | 0,491 | **0,362** |
| impostazioni | 0,448 | **0,311** |
| `/api/battery-health` | 1,150 | **0,114** |
| `/api/battery-vampire` | 2,427 | **0,929** |
| `/api/vehicle-status` | 0,551 | **0,447** |

Di quello che Mate mostra non è cambiato niente.

## Il costo era nel chiedere

`db_reader` apriva **una connessione SQLite nuova a ogni lettura**. `get_setting` costa circa 124 µs
non perché la query sia difficile, ma perché la connessione è nuova e la sua cache è fredda — e 119
query di quel modulo passano da lì, con una pagina che chiama decine di lettori.

Adesso c'è **una connessione di lettura per thread**. Viene lasciata quando il percorso del database
cambia, o quando **il file sotto quel percorso viene sostituito**: nella chiave c'è l'identità del
file, così un ripristino da backup viene visto e non ignorato in silenzio.

Condividerla non trattiene niente. È in sola lettura e SQLite dà a ogni statement la sua transazione
di lettura, quindi una commit del poller — un altro processo — si vede alla lettura successiva, e c'è
un test che prova esattamente questo. È la differenza dalla strada provata e scartata nella 4.5.2: un
*valore* tenuto in memoria invecchia nel momento in cui un altro scrive, una connessione condivisa no.

## Dimostrare un «no»

`/api/battery-health` era 1,150 s. Profilata su un database vero, l'intera stima costava 214 ms e
**184,57 ms erano una query sola, chiamata undici volte**: quella che chiede se durante la ricarica
c'era qualcuno in auto col riscaldamento o il condizionatore accesi — una ricarica così ha il rapporto
energia/SoC distorto e resta fuori dal calcolo.

Sembra economica (`SELECT 1 … LIMIT 1`) ed è proprio per questo che costava: senza un indice su quelle
due colonne, scoprire che **non** c'è nessuna corrispondenza vuol dire leggere ogni frame della
finestra. Cronometrata da sola su tutte le 33 ricariche di quel database: **618 ms**, piano
`SCAN positions`, e in nessuna di quelle 33 l'abitacolo era in uso. Un indice parziale che tiene solo
i frame in cui lo era — 2081 righe su 374.511 — trasforma il piano in una ricerca e quelle 33
verifiche in 0,10 ms.

## Altri tre orologi

La 4.5.2 aveva tolto il fuso orario da cinque cicli. Profilando quel che restava ne sono usciti altri
tre, tutti dentro closure invece che nel ciclo a vista:

* il riquadro del consumo da fermo leggeva l'impostazione **due volte per ogni sosta chiusa** — 1608
  letture per un riquadro;
* la striscia del polling scrive 288 finestre con due estremi ciascuna — **578 letture**, e il fuso
  era già risolto in testa a quella stessa funzione;
* il grafico della batteria lo leggeva una volta per ricarica datata.

## Il riquadro del consumo da fermo

`/api/battery-vampire` legge novanta giorni di righe di posizione e raggruppa i campioni consecutivi
in soste. Non c'è indice che aiuti: è un conto onesto su dati che solo crescono. Quello che non fa più
è costruire un `sqlite3.Row` per ognuno dei 284.505 frame. Sul banco, con le stesse 47 finestre e i
177 scarti ogni volta:

    4.5.0                          494,3 ms
    + fuso orario risolto una volta 301,5 ms
    + tuple sul cursore             209,2 ms

Sull'add-on, quell'ultimo passo vale **1,316 s → 0,929 s**.

La risposta non è solo uguale, è identica: tutta la risposta scritta in JSON dal lettore vecchio e da
quello nuovo dà **zero righe di differenza**.

## Due difetti che sono venuti fuori

Nessuno dei due era mai arrivato a qualcuno: per diventare raggiungibili servivano entrambi la
connessione condivisa, e sono corretti nella stessa release che li ha resi raggiungibili.

* I rifornimenti stanno in una tabella creata al primo uso, e tredici percorsi di lettura chiedevano
  di crearla su una connessione **in sola lettura**, la maggior parte avvolgendo quella chiamata e la
  propria query in un solo `except`. Su una connessione fresca non falliva mai, perché
  `CREATE TABLE IF NOT EXISTS` è un non-fare contro uno schema che già la contiene. Su una
  connessione aperta prima del primo rifornimento prova a scrivere, e da lì in poi la query dietro
  sarebbe stata saltata — un totale senza **un litro di benzina** di quelli inseriti.
* Il controllo aggiornamenti chiama GitHub con sei secondi di timeout e poi registra di aver girato,
  risolvendo il percorso del database quando il thread ci arriva. Ora scrive in quello per cui era
  stato programmato. Conta anche fuori dai test: quella scrittura apre il percorso col default di
  sqlite3, che **crea** un database vuoto se il file non c'è, quindi un lavoro puntato sul percorso
  sbagliato poteva lasciare lì qualcosa che sembra un'installazione nuova.

## Cosa questo non risolve, e perché

Ognuna di queste è stata misurata prima di essere lasciata stare:

* **Impostazioni, 0,311 s.** Tutte le letture dal database di quella pagina, sommate, costano
  **0,17 ms**. Il resto è comporre 149 KB di HTML. Nel lettore non c'è niente da correggere; per
  accorciarla i riquadri devono scaricarsi il proprio contenuto, una decisione alla volta, come già
  fa il riquadro «Collegamento al cloud».
* **La mappa, 0,362 s.** La query costa 24,5 ms e usa già il suo indice. Legge 47.936 punti per
  disegnarne 11.791 — tutti i viaggi mai registrati, che è quello a cui serve la pagina. Leggerli
  come tuple darebbe circa il 13%, al prezzo di riscrivere l'accesso alle righe di due funzioni
  condivise fra la mappa generale e quella del mese. La leva che conta è l'impostazione che c'è già,
  «quanti viaggi mostrare», che è su *tutti*.
* **`/api/vehicle-status`, 0,447 s.** Chiede all'auto, attraverso il cloud Leapmotor. Cronometrata da
  sola è 517 ms e **cinque query**: quello che resta è il cloud che risponde, non Mate. Le 213
  connessioni al database per chiamata che c'erano dentro non ci sono più.

## Verifica

- Tutta la suite: **4347 passati, 1 saltato**, un warning che c'era già. Ogni test nuovo è stato visto
  rosso prima, e i due difetti qui sopra sono stati ri-rotti per controllare che il test li prenda.
- Il prima/dopo qui sopra l'ha misurato il proprietario dell'add-on sul suo hardware, non su una
  macchina di sviluppo, e lo script si rifiuta di stampare un «dopo» se il container non è ripartito
  davvero.
- La risposta del riquadro del consumo da fermo è stata confrontata riga per riga, non solo
  cronometrata.

## Aggiornamento e ritorno indietro

Niente da fare. Al primo avvio viene aggiunto un indice parziale alla tabella `positions`, creato dopo
che le colonne che indicizza esistono. Del resto non cambia nulla né nello schema, né nelle
impostazioni, né nei dati salvati, quindi tornare alla 4.5.2 costa solo la velocità.
