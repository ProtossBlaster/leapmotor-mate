# Mate 4.7.18 — a backup restores on Windows, and a cloud failure says why

Restoring a database backup on MateDesktop for Windows answered an error; it restores now. A cloud
transport that fails names the failure in one word, in the log, the wizard and the bundle. And the
update instructions no longer point at an archived project.

---

## A restored backup goes into the live database, not over it — [#383](https://github.com/ProtossBlaster/leapmotor-mate/issues/383)

@matttiaromano could not import his database backup on MateDesktop: error 500. The restore wrote
the backup to a temporary file and replaced the live database with it. The poller holds the database
open for as long as it runs, and on Windows a file another process holds cannot be replaced.
Measured on Desktop 1.2.0 with Mate 4.7.17 in a Windows 11 VM: export the backup, import it back,
HTTP 500 with "[WinError 5] Accesso negato" on the replace. On macOS and Linux the replace goes
through, which is why the container and the Mac never showed it; the restore tests did not run in
the Windows job.

The restore now copies the backup's pages into the live database with SQLite's own backup API,
through SQLite's locks, and never touches the file name. The poller's connection reads the restored
data at once; the relaunch that follows still runs the migrations. Same machine, same backup, with
this change: 200, the services relaunched in two seconds, every row in place. A refused backup (not a
Mate database) no longer leaves its temporary file behind on Windows: the Windows CI job found that
the first time it ran the restore tests.

## A cloud transport that fails says why — [#381](https://github.com/ProtossBlaster/leapmotor-mate/issues/381)

@maxencedelesgues-droid's Home Assistant could not resolve the cloud's name for hours at a time.
Mate wrote 9,049 lines of "Cloud transport failed" in two weeks, and the setup page said
"stage=transport": the cause was readable only in the earlier library's wording, and the bundle did
not carry it. #384 arrived with the same line.

mate-api 0.1.0a15 names the failure a transport saw in one word from a fixed vocabulary:
`dns_failure`, `timeout`, `connection_refused`, `connection_reset`, `network_unreachable`,
`certificate_rejected`, `tls_failure`, `http_protocol`, `invalid_response`, `redirect_refused`,
`response_too_large`. No host, address or text from the system leaves the transport. The poll error
reads "Cloud transport failed: dns_failure"; a sign-in that failed in transport reads
"stage=transport (dns_failure)" in the wizard and in the setting Mate records; the diagnostics
bundle's info block prints "Last sign-in failure" when there was one.

## The update instructions no longer point at Watchtower — [#383](https://github.com/ProtossBlaster/leapmotor-mate/issues/383)

The Watchtower project the README, the Docker Hub text and the five manuals suggested for automatic
updates has been archived by its author (last change 17 December 2025) and no longer works with the
current Docker Desktop (@matttiaromano). The instructions keep what was already there: pull the
image and recreate the container.

## Upgrade impact

- Normal update. Nothing changes in the stored data.
- A restore from backup still relaunches Mate afterwards, as before; on Windows it now succeeds.
- Log lines and the wizard's sign-in error carry one more word after "Cloud transport failed" and
  "stage=transport". A tool that matched the old text exactly sees the longer one.
- The bundle has one more line, "Last sign-in failure", only on an install where a sign-in failed.

## Verification

- The restore: two tests hold the database open as the poller does and, off Windows, refuse the
  file replace as Windows does; both failed before, both pass now; the seven existing restore tests
  are unchanged, and the Windows CI job now runs them all. Measured on a Windows 11 VM before and
  after, as above.
- The transport: 13 cases in mate-api (each failure to its word, nothing else in the message, the
  login carrying the word), 236 upstream tests green; in Mate, three tests on the sign-in detail and
  one on the bundle line. Not tried against a real broken DNS: the word comes from the kind of
  exception the transport caught.
- Test suite green: 4979 passed, 3 skipped.

## Italiano

# Mate 4.7.18 — un backup si ripristina su Windows, e un guasto verso il cloud dice perché

Il ripristino di un backup del database su MateDesktop per Windows rispondeva un errore; adesso
ripristina. Un trasporto verso il cloud che fallisce dice in una parola perché, nel log, nella
guidata e nel pacchetto. E le istruzioni di aggiornamento non citano più un progetto archiviato.

---

## Un backup ripristinato entra nel database vivo, non lo sostituisce — [#383](https://github.com/ProtossBlaster/leapmotor-mate/issues/383)

@matttiaromano non riusciva a importare il backup del database su MateDesktop: errore 500. Il
ripristino scriveva il backup in un file temporaneo e lo sostituiva al database vivo. Il poller tiene
il database aperto per tutto il tempo in cui gira, e su Windows un file tenuto aperto da un altro
processo non si può sostituire. Misurato su Desktop 1.2.0 con Mate 4.7.17 in una VM Windows 11:
esporta il backup, reimportalo, HTTP 500 con «[WinError 5] Accesso negato» sulla sostituzione. Su
macOS e Linux la sostituzione passa, per questo il container e il Mac non l'hanno mai mostrato; i
test del ripristino non giravano nel job Windows.

Il ripristino adesso copia le pagine del backup dentro il database vivo con l'API di backup di
SQLite, passando dai suoi lock, e non tocca mai il nome del file. La connessione del poller legge
subito i dati ripristinati; il riavvio che segue esegue le migrazioni come prima. Stessa macchina,
stesso backup, con questa modifica: 200, servizi riavviati in due secondi, ogni riga al suo posto. Un
backup rifiutato (non un database di Mate) non lascia più il suo file temporaneo su Windows: l'ha
trovato il job Windows della CI la prima volta che ha eseguito i test del ripristino.

## Un trasporto verso il cloud che fallisce dice perché — [#381](https://github.com/ProtossBlaster/leapmotor-mate/issues/381)

L'Home Assistant di @maxencedelesgues-droid non risolveva il nome del cloud per ore di fila. Mate
ha scritto 9.049 righe «Cloud transport failed» in due settimane, e la pagina di configurazione
diceva «stage=transport»: la causa si leggeva solo nel messaggio della libreria precedente, e il
pacchetto non la portava. La #384 è arrivata con la stessa riga.

mate-api 0.1.0a15 dà un nome al guasto che il trasporto ha visto, una parola da un vocabolario
fisso: `dns_failure`, `timeout`, `connection_refused`, `connection_reset`, `network_unreachable`,
`certificate_rejected`, `tls_failure`, `http_protocol`, `invalid_response`, `redirect_refused`,
`response_too_large`. Nessun nome di host, indirizzo o testo del sistema esce dal trasporto. L'errore
del poll dice «Cloud transport failed: dns_failure»; un accesso fallito nel trasporto dice
«stage=transport (dns_failure)» nella guidata e nell'impostazione che Mate registra; il blocco info
del pacchetto di diagnostica stampa «Last sign-in failure» quando c'è stato un accesso fallito.

## Le istruzioni di aggiornamento non citano più Watchtower — [#383](https://github.com/ProtossBlaster/leapmotor-mate/issues/383)

Il progetto Watchtower che README, testo di Docker Hub e cinque manuali suggerivano per gli
aggiornamenti automatici è stato archiviato dal suo autore (ultima modifica 17 dicembre 2025) e non
funziona più con il Docker Desktop attuale (@matttiaromano). Le istruzioni tengono quello che c'era
già: scarica l'immagine e ricrea il container.

## Impatto dell'aggiornamento

- Aggiornamento normale. Nei dati salvati non cambia niente.
- Un ripristino da backup riavvia Mate dopo, come prima; su Windows adesso riesce.
- Le righe del log e l'errore di accesso della guidata portano una parola in più dopo «Cloud
  transport failed» e «stage=transport». Uno strumento che confrontava il testo vecchio alla lettera
  vede quello più lungo.
- Il pacchetto ha una riga in più, «Last sign-in failure», solo su un'installazione dove un accesso
  è fallito.

## Verifica

- Il ripristino: due test tengono il database aperto come fa il poller e, fuori da Windows,
  rifiutano la sostituzione del file come fa Windows; tutti e due fallivano prima, passano adesso; i
  sette test esistenti del ripristino sono invariati, e il job Windows della CI ora li esegue tutti.
  Misurato su una VM Windows 11 prima e dopo, come sopra.
- Il trasporto: 13 casi in mate-api (ogni guasto alla sua parola, nient'altro nel messaggio, il login
  che porta la parola), 236 test a monte verdi; in Mate tre test sul dettaglio dell'accesso e uno
  sulla riga del pacchetto. Non provato contro un DNS rotto vero: la parola viene dal tipo di
  eccezione che il trasporto ha catturato.
- Suite dei test verde: 4979 passed, 3 skipped.
