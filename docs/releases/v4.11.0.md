# Mate 4.11.0 — a T03's windows, a NAS shared folder, and the sunshade as a percent

Answers to two reports of 5 October — [#400](https://github.com/ProtossBlaster/leapmotor-mate/issues/400),
a T03 whose windows Mate would not send, and [#401](https://github.com/ProtossBlaster/leapmotor-mate/issues/401),
a NAS shared folder that stopped Mate at start — and three changes by @arekm:
[#391](https://github.com/ProtossBlaster/leapmotor-mate/pull/391),
[#394](https://github.com/ProtossBlaster/leapmotor-mate/pull/394) and
[#399](https://github.com/ProtossBlaster/leapmotor-mate/pull/399).

---

## A T03's windows — [#400](https://github.com/ProtossBlaster/leapmotor-mate/issues/400), @dilianpenchev-a11y, @arekm

@dilianpenchev-a11y's T03 opened no window from Mate: the page answered "Command not sent:
ability_absent for 230", and nothing reached the cloud. Since 4.0.0, Mate's command contract asks
for an ability code before the windows command, and it asked for 12. The B10 and the C10 declare 12;
a T03 declares 36 instead — @arekm found the pair. So on a T03 Mate hid the Windows tile's Open /
Close button, and the slider it left was refused inside Mate. The contract also allowed positions
0–10 only, the scale of the B10, the C10 and the B05, while a T03 takes 0–100.

- Either code now lets the command through, so no model name is needed.
- A car that declares 36 takes a position from 0 to 100; the others keep 0 to 10. Mate already sent
  each model its own scale: 20 % is "20" to a T03 and "2" to a B10.
- Where the car's own list does refuse the windows, the slider now hides with the button. The page
  hid the buttons only: the slider sends from a script, and the rule that hides a command looked for
  buttons.
- A command Mate does not send now leaves its reason in the log — "Command not sent: ability_absent
  for 230" — where the line read "MateAPIError". Any other failure still logs only its type.
- The support bundle lists what the account may do with the car — its rights and modules from the
  cloud's vehicle list, and whether the car is shared with it — beside the abilities, as @arekm
  suggested: a command needs both.

Measured with the cloud's transport replaced by a recorder: a T03 declaring the abilities of #400
now sends cmd 230 with 0, 9, 20, 66 and 100; 4.10.0 sent none of them. The reporter's own bundle shows
the same car sent 4, 11, 66, 99, 72 and 100 on 21–22 September, before 4.0.0, each answered by the
cloud with code 0. **Not tried on a T03 since the change.**

The other differences in @arekm's table are left as they are for now: each needs a car to show which
code it means.

## A NAS shared folder — [#401](https://github.com/ProtossBlaster/leapmotor-mate/issues/401), @awooganl

@awooganl's Synology ran Mate 3.19.2 with a shared folder as `/data`; from 4.0.0 every image stopped
at once with "ValueError: Private directory permissions required". Since 4.0.0, Mate requires the
folders that hold the account's files — certificates and keys — and the one-time backup it takes
before the 4.0.0 migration, the first thing it does at start, to be private: no permission for group
or others. On storage that does not keep modes every file reads as 0777 whatever was asked — a FAT
disk does this, and a NAS share that maps its own ACLs onto the modes can — so the check could never
pass there. Who reads such a folder is decided by the storage's own permissions, which the bits do not
show.

- Mate now tells the two apart: it creates a probe file and a probe folder with private modes, reads
  them back and removes them. Where they read back private, the folder is checked as before and refused
  if it is open: on an ordinary disk nothing changes.
- On storage that does not keep modes, Mate starts, and writes once in the log: "… does not keep file
  permissions (a NAS shared folder with its own ACLs, for example): who can read the account files
  there is decided by that folder's own permissions".
- The startup backup copies contents only and sets the modes afterwards, letting a refusal pass:
  copying a file's mode along with it failed the whole backup where the storage refuses a change of
  mode.

Measured on a FAT disk (Linux vfat: every file reads 0777, a change of mode is accepted and ignored),
the same 128 MB image as `/data`:

- the 4.10.0 image stopped after one second with the ValueError of #401;
- this version answered `/healthz` and served its first page at once; its backup held the database, the
  certificates and the account files, no probe was left behind, and the log carried the one line.
  Started again on Mate's own data with the backup removed, it did the same.

**Not tried on a Synology.**

## The sunshade as a percent — [#391](https://github.com/ProtossBlaster/leapmotor-mate/pull/391), @arekm

Signal 1724 is how far the sunshade is open, the number the car's own screen shows; Mate kept it as
open or closed. Now:

- the roof tile on the Vehicle page and the sunshade tile on Commands say how far it is open. Stopped
  part-way, the Commands tile offers both Open and Close — the two positions the car acts on — with a
  read-only bar for the percent;
- the Events page lists where the sunshade stopped, as a moment rather than a span;
- Home Assistant gets a `Sunshade Position` sensor in % (0 = closed); the `Sunshade` binary sensor
  stays as it was, on for any opening.

## A drive the cloud reads as 0.0 kWh — [#394](https://github.com/ProtossBlaster/leapmotor-mate/pull/394), @arekm

The cloud files some short drives at 0.0 kWh. Mate took that answer for a miss: the trip stayed
marked as waiting for the cloud, was asked every five minutes for six hours, and ended with no energy.

- Where the battery read the same at both ends of the drive, the zero is now the trip's figure, and
  it counts in every average with its kilometres.
- Where the battery fell or was not read, a zero is still no answer — five kilometres cannot cost
  nothing — and so is a total below zero.
- A merged trip is judged as its whole group, as "Convert" already judged it.
- A month's zero total goes through the same check against Mate's own trips as any other total.

Measured on a copy of a real database (a B10): 58 drives, 3.9 km in all, carry a zero the battery
does not confirm — 53 imported from the cloud's history without a state of charge, 2 of 0 km, 3 of
Mate's own with the battery falling. They no longer count in an average: September reads 15.7
kWh/100 km in the Trips calendar and in the Statistics table, where it read 15.5, as the period card
already did. The trips' own pages are unchanged.

## The info marks open on a tap — [#399](https://github.com/ProtossBlaster/leapmotor-mate/pull/399), @arekm

The ⓘ beside the outside temperature on the Overview's status card and beside the Wallbox's maximum
current had only the browser's tooltip, which a tap — and the Home Assistant app — never opens; they
now open on a tap, like the trip page's. A new ⓘ beside READY says what the state means.
[#398](https://github.com/ProtossBlaster/leapmotor-mate/pull/398), also @arekm, makes a browser test
let the page settle before it reads a figure.

## Upgrade impact

- Normal update. The `positions` table gains a `sunshade_pct` column at the first start; the old
  `sunshade_open` stays, unused. Nothing is migrated, recomputed or deleted.
- An average that took a 0.0 kWh drive the battery does not confirm moves: on the database above,
  September 15.5 → 15.7 kWh/100 km.
- On storage that does not keep file permissions, Mate starts and logs one warning. Going back to
  4.10.0 there stops Mate again.

## Verification

- CI green on the tag: 5,333 passed, 1 skipped (a test that needs a local-only file), plus 48
  on the Windows job; the check that the released desktop shell still runs this Mate is green.
- Locally, in the CI's image with Node.js and a MateDesktop checkout added — so that nothing is
  skipped: 5,334 passed.
- Of the 17 new tests, 14 fail on 4.10.0 and pass now: the T03's command for five positions, the page
  offering a T03 its windows, the slider hiding with the buttons, the log keeping the contract's
  words, the backup on a folder that keeps no modes — with a change of mode ignored and refused — and
  the account's rights in the bundle. The 3 guards pass on both: a B10's native value, the log of any
  other failure, an open folder on an ordinary disk still refused.
- mate-api 0.1.0a16, which carries the windows and storage changes: 244 tests run, 241 pass and 3 are
  skipped. Of its 8 new tests, the 4 that check the change fail on 0.1.0a15 — the storage one on a
  copy with the probe taken out — and the 4 guards pass.
- The FAT-disk start above, with the 4.10.0 image and with this version's.

## I finestrini di una T03 — [#400](https://github.com/ProtossBlaster/leapmotor-mate/issues/400), @dilianpenchev-a11y, @arekm

La T03 di @dilianpenchev-a11y non apriva nessun finestrino da Mate: la pagina rispondeva «Command not
sent: ability_absent for 230», e al cloud non arrivava niente. Dalla 4.0.0 il contratto dei comandi di
Mate chiede un codice di abilità prima del comando dei finestrini, e chiedeva il 12. La B10 e la C10
dichiarano il 12; una T03 dichiara invece il 36 — la coppia l'ha trovata @arekm. Così su una T03 Mate
nascondeva il bottone Apri / Chiudi del riquadro Finestrini, e il cursore rimasto veniva rifiutato
dentro Mate. Il contratto ammetteva anche solo le posizioni 0–10, la scala di B10, C10 e B05, mentre una
T03 prende 0–100.

- Adesso basta uno dei due codici, quindi non serve il nome del modello.
- Un'auto che dichiara il 36 prende una posizione da 0 a 100; le altre restano a 0–10. Mate mandava già
  a ogni modello la sua scala: il 20 % è «20» per una T03 e «2» per una B10.
- Dove è la lista dell'auto stessa a rifiutare i finestrini, il cursore adesso sparisce insieme al
  bottone. La pagina nascondeva solo i bottoni: il cursore invia da uno script, e la regola che nasconde
  un comando cercava bottoni.
- Un comando che Mate non invia lascia adesso nel registro il suo motivo — «Command not sent:
  ability_absent for 230» — dove la riga diceva «MateAPIError». Ogni altro errore scrive ancora solo il
  suo tipo.
- Il pacchetto di supporto elenca cosa può fare l'account con l'auto — i suoi permessi e moduli dalla
  lista veicoli del cloud, e se l'auto è condivisa con lui — accanto alle abilità, come suggerito da
  @arekm: un comando ha bisogno di entrambi.

Misurato con il trasporto verso il cloud sostituito da un registratore: una T03 che dichiara le abilità
della #400 adesso manda il comando 230 con 0, 9, 20, 66 e 100; la 4.10.0 non ne mandava nessuno. Il
pacchetto del segnalatore mostra che la stessa auto ha mandato 4, 11, 66, 99, 72 e 100 il 21–22
settembre, prima della 4.0.0, ognuno con risposta codice 0 dal cloud. **Non provato su una T03 dopo la
modifica.**

Le altre differenze della tabella di @arekm per ora restano come sono: per ognuna serve un'auto che
mostri quale codice vuol dire.

## La cartella condivisa di un NAS — [#401](https://github.com/ProtossBlaster/leapmotor-mate/issues/401), @awooganl

Il Synology di @awooganl faceva girare Mate 3.19.2 con una cartella condivisa come `/data`; dalla 4.0.0
ogni immagine si fermava subito con «ValueError: Private directory permissions required». Dalla 4.0.0
Mate pretende private — nessun permesso per il gruppo o per gli altri — le cartelle che tengono i file
dell'account, certificati e chiavi, e il backup che fa una volta sola prima della migrazione della
4.0.0, la prima cosa che fa all'avvio. Su un disco che non tiene i permessi ogni file si legge 0777
qualunque cosa sia stata chiesta — lo fa un disco FAT, e lo può fare una condivisione di NAS che
proietta le sue ACL sui permessi — quindi lì il controllo non poteva mai passare. Chi legge una
cartella così lo decidono i permessi del disco stesso, che quei bit non mostrano.

- Adesso Mate distingue i due casi: crea un file e una cartella di prova con permessi privati, li
  rilegge e li cancella. Dove si rileggono privati, la cartella si controlla come prima e si rifiuta se
  è aperta: su un disco normale non cambia niente.
- Su un disco che non tiene i permessi, Mate parte, e scrive una volta nel registro: «… does not keep
  file permissions (a NAS shared folder with its own ACLs, for example): who can read the account files
  there is decided by that folder's own permissions».
- Il backup all'avvio copia solo il contenuto e imposta i permessi dopo, lasciando passare un rifiuto:
  copiare il permesso di un file insieme al file faceva fallire tutto il backup dove il disco rifiuta un
  cambio di permessi.

Misurato su un disco FAT (vfat di Linux: ogni file si legge 0777, un cambio di permessi viene accettato
e ignorato), la stessa immagine da 128 MB come `/data`:

- l'immagine 4.10.0 si è fermata dopo un secondo con il ValueError della #401;
- questa versione ha risposto subito a `/healthz` e ha servito la sua prima pagina; il suo backup
  conteneva il database, i certificati e i file dell'account, non è rimasta nessuna prova, e il
  registro aveva l'unica riga. Riavviata sui dati di Mate stessa con il backup tolto, ha fatto lo
  stesso.

**Non provato su un Synology.**

## La tendina in percentuale — [#391](https://github.com/ProtossBlaster/leapmotor-mate/pull/391), @arekm

Il segnale 1724 dice quanto è aperta la tendina, il numero che mostra lo schermo dell'auto; Mate lo
teneva come aperta o chiusa. Adesso:

- il riquadro del tetto nella pagina Veicolo e quello della tendina in Comandi dicono quanto è aperta.
  Ferma a metà, il riquadro di Comandi offre sia Apri sia Chiudi — le due posizioni che l'auto esegue —
  con una barra di sola lettura per la percentuale;
- la pagina Eventi elenca dove si è fermata la tendina, come un momento e non come un intervallo;
- Home Assistant riceve un sensore `Sunshade Position` in % (0 = chiusa); il sensore binario
  `Sunshade` resta com'era, acceso a qualsiasi apertura.

## Un viaggio che il cloud legge 0,0 kWh — [#394](https://github.com/ProtossBlaster/leapmotor-mate/pull/394), @arekm

Il cloud registra alcuni viaggi brevi a 0,0 kWh. Mate prendeva quella risposta per una mancanza: il
viaggio restava in attesa del cloud, veniva richiesto ogni cinque minuti per sei ore, e finiva senza
energia.

- Dove la batteria segnava lo stesso valore ai due capi del viaggio, lo zero adesso è la cifra del
  viaggio, e conta in ogni media con i suoi chilometri.
- Dove la batteria è scesa o non è stata letta, uno zero resta una non-risposta — cinque chilometri non
  possono costare niente — e lo stesso vale per un totale sotto zero.
- Un viaggio unito si giudica come tutto il suo gruppo, come già faceva «Converti».
- Uno zero del cloud per un mese passa lo stesso controllo contro i viaggi di Mate di qualunque altro
  totale.

Misurato su una copia di un database vero (una B10): 58 viaggi, 3,9 km in tutto, hanno uno zero che la
batteria non conferma — 53 importati dalla cronologia del cloud senza stato di carica, 2 da 0 km, 3 di
Mate con la batteria scesa. Non contano più in nessuna media: settembre dice 15,7 kWh/100 km nel
calendario dei Viaggi e nella tabella di Statistiche, dove diceva 15,5, come già la scheda del periodo.
Le pagine dei singoli viaggi non cambiano.

## Le ⓘ si aprono al tocco — [#399](https://github.com/ProtossBlaster/leapmotor-mate/pull/399), @arekm

Le ⓘ accanto alla temperatura esterna nella scheda di stato della Panoramica e accanto alla corrente

test nel browser che la pagina si assesti prima di leggere una cifra.

## Impatto dell'aggiornamento

- Aggiornamento normale. La tabella `positions` riceve una colonna `sunshade_pct` al primo avvio; la
  vecchia `sunshade_open` resta, inutilizzata. Niente viene migrato, ricalcolato o cancellato.
- Una media che prendeva un viaggio da 0,0 kWh non confermato dalla batteria si sposta: sul database
  sopra, settembre 15,5 → 15,7 kWh/100 km.
- Su un disco che non tiene i permessi dei file, Mate parte e scrive un avviso nel registro. Tornare
  alla 4.10.0 lì ferma di nuovo Mate.
