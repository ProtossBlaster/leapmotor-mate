# Mate 4.4.0 — the installations left behind, and the login every half hour

Two things that belong together: the accounts that were kept on the old cloud client without
ever being asked again, and what that client cost them.

## Every model qualifies for the independent client (#298, #327, #330)

Mate 4 runs one of two cloud clients, and which one is decided once, by a probe that runs in a
subprocess. Since 4.2.0 that probe answers with the models it actually saw, and its own comment
says *every model qualifies*. The code that read its verdict did not:

```python
if result == {'state': 'qualified', 'capabilities': ['B10']}:
```

A C10 account answered `['C10']`, matched nothing, and was kept on the **bundled SDK** — which is
where the consumption reads went out unsigned until 4.3.0 (#327, #330), and where the cloud
trip-history card does not exist at all (#298). The gate had been opened inside the child and left
shut in the parent, on the other side of a subprocess boundary.

And the verdict is sticky: the decision is kept per release and returned untouched while it
matches, and that marker had read `4.0.0` through 4.1, 4.2, 4.3 and 4.3.1. An installation refused
once — on a day the cloud was refusing logins, say — was never asked again by any later version.

Both are fixed. The verdict is accepted from an account of any model, and the release marker moves,
which is this file's own way of asking once more where the rule changed. **Installations that were
left on the old client migrate at the next start**, which is what 4.0.0 always intended for them.

## A session is renewed, not bought again with a login

Measured against the live cloud on 27 September: the login response carries a **refresh token**,
states the access token's life as **7200 s** and the refresh token's as **604799 s — seven days**,
and `POST /base/base-user/token/v1/refresh` answers with a complete new session — access token,
refresh token, signing parameters — without a login and without re-issuing the account certificate.

Mate kept none of it. Every session was capped at thirty minutes, a prudent bound chosen when
nothing said otherwise, and `token_refresh()` did the opposite of its name: it cleared the expiry
and logged in again. On an account the cloud has been rationing since 17 September, that was
**48 logins a day**.

| | logins per day |
|---|---|
| before | ~48 |
| the token's real life alone | ~12 |
| with renewal | **about one a week** |

The library's own bound is now the cloud's stated lifetime, the saved session carries its refresh
material, and a renewal falls back to a login only when there is nothing to renew with or the cloud
refuses — which must never leave Mate holding a dead session.

This is the first lever on the login wall behind #296 and beta #49. It does not open a door the
cloud has closed; it stops knocking on it every half hour.

## Verification

4119 tests in the environment the project pins. Both halves were run end to end on the lab against
the live cloud. The renewal, from the adapter's own request log — the four logins before it are the
old behaviour photographed:

```
16:51:55  /base/base-user/account/v1/login  -> 200/0
17:20:52  /base/base-user/account/v1/login  -> 200/0
17:49:47  /base/base-user/account/v1/login  -> 200/0
18:18:42  /base/base-user/account/v1/login  -> 200/0
18:36:44  /base/base-user/account/v1/login  -> 200/0   (fallback: no refresh material yet)
18:36:46  /base/base-user/token/v1/refresh  -> 200/0   (the renewal)
```

And the re-qualification, with a decision planted to look exactly like an installation refused by
an earlier release: `legacy / 4.0.0 / qualification_failed` in, **`independent / qualified`** out,
in 1.2 seconds and without spending a login.

## Update and rollback

Ordinary update: Docker and both Home Assistant add-ons use the same 4.4.0 payload. No credential,
PIN or migration step, and nothing in the database changes shape. An installation that was kept on
the bundled SDK changes client at first start — that is the point of this release — and with it
gains the cloud trip-history card and the per-vehicle command rules 4.2.0 described.

## Italiano

**Ogni modello qualifica per il client indipendente (#298, #327, #330).** Mate 4 gira su uno di due
client, e quale lo decide una sonda in un sottoprocesso. Dalla 4.2.0 la sonda risponde coi modelli
che ha visto, e nel suo commento c'è scritto *ogni modello qualifica*. Chi ne leggeva il verdetto,
no: confrontava la risposta con un `['B10']` letterale. Un account C10 rispondeva `['C10']`, non
combaciava con niente e restava sulla **libreria vecchia** — dove le letture dei consumi partivano
senza firma fino alla 4.3.0 (#327, #330) e dove la card dello storico viaggi non esiste (#298). Il
cancello era stato aperto dentro il processo figlio e lasciato chiuso nel padre.

E il verdetto è appiccicoso: si conserva per release e viene restituito intatto finché combacia, e
quel segnaposto ha letto `4.0.0` attraverso la 4.1, la 4.2, la 4.3 e la 4.3.1. Chi era stato
respinto una volta — magari in un giorno in cui il cloud rifiutava i login — non è più stato
interrogato da nessuna versione. Corretti entrambi: **le installazioni rimaste indietro passano al
client nuovo al primo avvio**, che è ciò che la 4.0.0 aveva sempre inteso per loro.

**Una sessione si rinnova, non si ricompra con un login.** Misurato sul cloud vero il 27 settembre:
la risposta di login porta un **token di rinnovo**, dichiara la vita del token d'accesso in
**7200 s** e quella del rinnovo in **604799 s, sette giorni**, e l'endpoint di rinnovo risponde con
una sessione intera — token, rinnovo e parametri di firma — senza login e senza riemettere il
certificato di account. Mate non ne teneva niente: ogni sessione era tagliata a mezz'ora, una scelta
prudente di quando non sapevamo, e `token_refresh()` faceva il contrario del proprio nome. Su un
account razionato dal 17 settembre erano **48 login al giorno**; adesso sono circa **uno a
settimana**. È la prima leva sul muro dei login dietro a #296 e alla beta #49: non apre una porta
che il cloud ha chiuso, smette di bussarci ogni mezz'ora.

Aggiornamento ordinario, senza credenziali, PIN o migrazione. Chi era tenuto sulla libreria vecchia
cambia client al primo avvio — è il senso di questa release — e con quello ottiene la card dello
storico viaggi dal cloud e le regole per comando descritte dalla 4.2.0.
